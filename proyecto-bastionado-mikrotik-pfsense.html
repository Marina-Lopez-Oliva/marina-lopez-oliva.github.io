01_contexto

Defensa en profundidad para el IES Camp de Morvedre

El conjunto de prácticas documenta el diseño, implementación y fortificación de una red perimetral segura para un centro educativo, utilizando una arquitectura de doble firewall (Back‑to‑Back): pfSense como frontend (frontera externa) y MikroTik RouterOS como backend (seguridad interna). Se ha aplicado segmentación física y lógica (VLANs), aislamiento de la DMZ, despliegue de servicios web seguros, monitorización proactiva con The Dude + Telegram, mitigación de ataques MiTM (ARP Poisoning, MAC Flooding) y defensa contra DoS/SYN Flood, culminando en una VPN site‑to‑site con WireGuard para conectar sedes remotas bajo el principio de mínimo privilegio.

Todas las prácticas fueron validadas en GNS3 con equipos virtuales (pfSense, MikroTik CHR, switches Cisco, Ubuntu Server, Kali Linux) y posteriormente documentadas siguiendo estándares como CIS Controls v7.1 y NIST SP 800-53.

02_arquitectura

Topología de doble firewall y segmentación

FRONTEND (pfSense)

  • Interfaz WAN (conexión a internet simulada)
  • Interfaz DMZ (red 192.168.1.0/24) – servidor web y backend
  • Reglas NAT + Port Forwarding (HTTP/HTTPS/SSH)
  • Bloqueo de tráfico saliente desde DMZ (solo DNS/NTP permitido)

BACKEND (MikroTik)

  • VLAN 10 · Administración (192.168.30.0/24)
  • VLAN 11 · Alumnado (192.168.31.0/24)
  • VLAN 99 · Gestión (192.168.100.0/28) – administración de switches
  • Trunk hacia switches Cisco con VLANs departamentales
  • Reglas firewall INPUT/FORWARD con default drop

DMZ Y SERVIDORES

  • Ubuntu Server (web corporativa + SFTP) en 192.168.10.10
  • Acceso web desde IT permitido; SSH solo desde IP de administrador
  • NAT con redirección de puertos desde WAN de pfSense
  • Bloqueo de conexiones iniciadas desde DMZ hacia IT

VLAN DE GESTIÓN Y MONITORIZACIÓN

  • Bridge en pfSense para extender VLAN 99 a ambas redes (DMZ e IT)
  • The Dude (servidor en MikroTik, cliente con Wine en Linux)
  • Alertas a Telegram por CPU >50% y pérdida de conectividad
  • SNMPv3 para monitorización de servidor web

04_incidencias

Problemas reales y soluciones aplicadas

PROBLEMA — ARP poisoning

Desde Kali se envenena la tabla ARP del gateway y la víctima (VPCS) mediante ettercap, redirigiendo todo el tráfico.

SOLUCIÓN

Configuración de switchport protected en los puertos de acceso de los switches. Así se aíslan los puertos y el tráfico no puede ser interceptado por el atacante.

PROBLEMA — MAC flooding

La herramienta macof inunda la tabla CAM del switch con MACs falsas, forzando un comportamiento de hub y permitiendo sniffing.

SOLUCIÓN

Activación de port-security en la interfaz del atacante con límite de 2 MACs y violación shutdown. El switch deshabilita el puerto al superar el límite.

PROBLEMA — Ataque DoS (Slow HTTP headers)

El servidor web de la DMZ queda inaccesible (timeout) y el firewall MikroTik se satura, impidiendo incluso la administración.

SOLUCIÓN

Reglas en la tabla RAW: límite de 32 paquetes cada 10 segundos, adición automática de IPs atacantes a una lista de direcciones y bloqueo posterior de todo el tráfico entre atacante y víctima.

PROBLEMA — SYN flood sin mitigación

El servidor web deja de responder y la tabla de conexiones del router se llena de estados syn-sent.

SOLUCIÓN

Activación de /ip settings set tcp-syncookies=yes en MikroTik. El firewall ya no mantiene estado para medias conexiones, evitando la saturación.

PROBLEMA — Acceso administrativo no autorizado

Logs del MikroTik muestran intentos de login SSH desde IPs fuera de la VLAN de gestión (por ejemplo, desde el atacante Kali).

SOLUCIÓN

Reglas en cadena INPUT que solo permiten SSH y HTTPS desde la subred 192.168.100.0/28. Bloqueo explícito del resto. Además se deshabilitó el usuario admin por defecto.
