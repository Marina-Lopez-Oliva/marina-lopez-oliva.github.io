01_contexto

Seguridad integrada en el ciclo de vida del desarrollo de software

Este proyecto agrupa todos los ejercicios y el proyecto final de la asignatura de Puesta en Producción Segura (PPS), que abarca desde la identificación de vulnerabilidades en código (OWASP Top 10) hasta la implementación de un pipeline CI/CD seguro siguiendo prácticas DevSecOps.

Los contenidos incluyen:

  • Ejercicios de vulnerabilidades: detección de problemas en fragmentos de código (SQL Injection, XSS, almacenamiento inseguro, deserialización, exposición de datos, IDOR, cifrado débil, subida de ficheros, etc.) y propuesta de soluciones.
  • Examen teórico: preguntas sobre overflow, vulnerabilidades en lenguajes de alto nivel, pruebas de software y análisis de código vulnerable (XSS).
  • Evaluación de riesgos (MAGERIT): mapeo de datos sensibles, identificación de controles, plantilla de riesgos y código mejorado para una aplicación de gestión de pacientes.
  • Seguridad para servicios web (OWASP): diseño seguro de endpoints, configuración de gateways, monitorización de APIs.
  • Análisis de tráfico web y detección de vulnerabilidades OWASP: identificación de malas prácticas en capturas de tráfico HTTP y correlación con OWASP Top 10.
  • Corrección de código vulnerable (API REST): identificación de vulnerabilidades (SQLi, credenciales en texto plano, falta de autenticación, IDOR, debug mode) y desarrollo de código seguro.
  • DevSecOps (2 ejercicios): análisis de incumplimientos por fases (Plan, Code, Build, Test, Release, Deploy, Monitor) en dos escenarios diferentes, con propuestas de mejora.
  • Seguridad en apps móviles: riesgos principales, comparativa Android/iOS, OWASP Mobile Top 10, técnicas de detección, herramientas (MobSF, Frida, Burp, etc.) y buenas prácticas.
  • Proyecto final PPS: análisis completo de una aplicación Flask vulnerable (11 vulnerabilidades), corrección de código, implementación de cabeceras de seguridad HTTP, análisis SAST con Bandit, construcción de Dockerfile seguro, pipeline CI/CD diagramado y gatekeeping.
02_fases

Metodología DevSecOps aplicada

PLAN

  • Definición de requisitos de seguridad medibles.
  • Análisis de amenazas documentado (modelado de amenazas).
  • Requisitos de cumplimiento normativo (RGPD/LOPD).
  • Planificación de validación de entradas y uso de parámetros.

CODE (Desarrollo seguro)

  • Consultas parametrizadas (SQL Injection).
  • Hashing de contraseñas (bcrypt / werkzeug.security).
  • Escape de salida HTML (XSS).
  • Validación de entrada (regex, whitelist).
  • Uso de subprocess.run con shell=False (command injection).
  • Gestión de secretos mediante variables de entorno (no hardcodeados).

BUILD (Análisis estático + SCA)

  • SAST: Semgrep / Bandit (detección de SQLi, XSS, command injection, debug=True).
  • SCA: OWASP Dependency-Check / pip-audit / Snyk (detección de CVEs en dependencias).
  • SBOM: Syft (CycloneDX/SPDX).
  • Gatekeeping: bloqueo si se detectan vulnerabilidades críticas.

TEST (DAST + pruebas de seguridad)

  • Pruebas unitarias con mocks/stubs (aislamiento de servicios externos).
  • Pruebas de integración con entornos efímeros.
  • DAST: ZAP, Burp Suite (pruebas de inyección, bypass de autenticación).
  • Pentesting interno antes del release.

RELEASE + DEPLOY

  • Security gate automático (no release si SAST/SCA detectan críticos).
  • Aprobación explícita del responsable de seguridad.
  • Eliminación de secretos del historial de Git.
  • Uso de variables de entorno para configuración sensible.
  • Proxy inverso (Nginx) con TLS (HTTPS).
  • Contenedor con usuario no root y HEALTHCHECK.

MONITOR

  • Logs centralizados (SIEM).
  • Alertas automáticas (patrones de ataque, fuerza bruta).
  • No exponer datos sensibles en logs (contraseñas, tokens).
  • Plan de respuesta a incidentes.

04_hallazgos

Vulnerabilidades críticas corregidas

V-01 – Secret key hardcodeada

Cualquier atacante con acceso al repositorio podía forjar cookies de sesión Flask (HMAC-SHA1).

SOLUCIÓN

Cargar SECRET_KEY de variable de entorno o generar token aleatorio en desarrollo con secrets.token_hex(32).

V-03 – SQL Injection

Concatenación directa de username/password en consulta SQL → acceso sin credenciales (OR 1=1).

SOLUCIÓN

Consulta parametrizada con placeholder ?. SQLite trata los inputs como datos literales, no como código.

V-07 – Command Injection

subprocess.getoutput("ping -c 1 " + host) con payload 127.0.0.1; cat /etc/passwd.

SOLUCIÓN

Validación de host con regex + subprocess.run([...], shell=False). Sin shell, los metacaracteres no se interpretan.

V-10 – Debug mode en producción

app.run(debug=True) expone debugger interactivo de Werkzeug → ejecución remota de código Python.

SOLUCIÓN

debug=False, usar gunicorn/uwsgi detrás de proxy inverso. Eliminación completa del debugger.
