01_contexto

Estrategia de ciberseguridad para una empresa de construcción

El proyecto se desarrolla para Anonym Construcciones S.L., una empresa del sector de la construcción con sede central, obras distribuidas y personal que teletrabaja. Se han identificado activos críticos (servidores, ERP, datos de clientes, AD), amenazas relevantes (phishing, ransomware, pérdida de dispositivos, cortes eléctricos) y vulnerabilidades como falta de MFA, backups sin verificar o ausencia de SAI.

Siguiendo la metodología MAGERIT (alineada con ENS e ISO/IEC 27001), se ha elaborado un inventario de activos, un análisis de riesgos (impacto × probabilidad), un Plan Director de Seguridad (PDS) con medidas priorizadas (P1, P2, P3) y un conjunto de playbooks de respuesta a incidentes para escenarios reales: fuerza bruta SSH, ransomware, robo de portátil y corte eléctrico.

Además, se ha desplegado un laboratorio con Wazuh, Suricata, OPNsense, Windows Server (AD) y Kali Linux para simular ataques y validar la detección y correlación de eventos.

02_arquitectura

Enfoque metodológico y laboratorio

METODOLOGÍA MAGERIT

  • Inventario de activos por categorías (datos, hardware, software, personas, servicios, infraestructura)
  • Valoración D/C/I/T (disponibilidad, confidencialidad, integridad, trazabilidad)
  • Identificación de amenazas según catálogo MAGERIT
  • Cálculo de riesgo: Impacto × Probabilidad (escala 1-5)
  • Clasificación: muy alto (≥16), alto (12-15), medio (8-11), bajo (<8)
  • Definición de salvaguardas y plan de tratamiento (PDS)

PLAN DIRECTOR DE SEGURIDAD (PDS)

  • Prioridades: P1 (crítico, 0-3 meses), P2 (alto, 3-6 meses), P3 (medio, 6-12 meses)
  • Medidas P1: MFA, formación anti-phishing, backups 3-2-1, EDR, gestión parches, hardening AD, seguridad correo, auditorías KPIs
  • Medidas P2: control de accesos ERP, clasificación de información, SLA proveedores, segmentación red, SAI, cifrado dispositivos móviles, simulacros
  • Medidas P3: seguridad física sala servidores, política USB, hardening portal web
  • Presupuesto anual ajustado a 10.000€

LABORATORIO DE SIMULACIÓN

  • Red privada 10.0.2.0/24 con segmentación por integrante
  • OPNsense firewall (10.0.2.100) · Wazuh SIEM (10.0.2.6)
  • Ubuntu Desktop con Joomla (10.0.2.40) · Windows Server AD (10.0.2.69)
  • Kali Linux atacante (10.0.2.35 / 10.0.2.50)
  • Ataques simulados: fuerza bruta SSH (Hydra), escaneo con Nmap, explotación de Joomla (CVE-2023-23752), movimiento lateral hacia AD
  • Correlación de eventos en Wazuh y reconstrucción de la kill chain

Extracción de logs de SSH (268 fallos + 1 éxito), logs web (método XRAP de Nmap), eventos de Windows (EventID 4624). Correlación para reconstruir la kill chain: Reconocimiento → Fuerza bruta → Acceso → Movimiento lateral. Alertas personalizadas en Wazuh.

04_incidencias

Hallazgos críticos y medidas propuestas

HALLAZGO — Ausencia de MFA en accesos críticos

El atacante pudo autenticarse mediante fuerza bruta SSH porque no existía segundo factor de autenticación.

SOLUCIÓN P1

Implantación de MFA en ERP, correo, servicios cloud y accesos remotos. Configuración de políticas de contraseñas robustas.

HALLAZGO — Backups sin pruebas de restauración

Durante la simulación de ransomware, se descubrió que las copias de seguridad no se verificaban, lo que podría imposibilitar la recuperación.

SOLUCIÓN P1

Adopción del modelo 3-2-1 y realización de pruebas de restauración mensuales con registro de RTO/RPO real.

HALLAZGO — Cortes eléctricos sin SAI

Un corte de suministro provocaría la caída inmediata de servidores, AD, ERP y pérdida de datos en proceso.

SOLUCIÓN P2

Instalación de SAI para servidor crítico y procedimientos de apagado seguro. Redundancia de comunicaciones (segundo ISP).

HALLAZGO — Usuarios con privilegios excesivos

El administrador externo (PER-09) tenía acceso completo sin supervisión ni separación de funciones.

SOLUCIÓN P1

Control de privilegios, cuentas nominativas, revisión de cambios críticos y doble autorización para modificaciones en firewall.

HALLAZGO — Falta de segmentación de red

Un atacante que compromete el servidor web (Joomla) puede moverse lateralmente hacia Active Directory.

SOLUCIÓN P2

Propuesta de VLANs: Gestión (10), Usuarios (20), DMZ web (30), Obras (40), Monitorización (50). Reglas de firewall estrictas entre VLANs.
